# Koordinator 十节点混部资源利用率测试设计

## 1. 目标

在一个包含 10 个节点的独立资源池内，使用可重复的模拟在线业务和 BE 离线任务，验证 Koordinator 混部能否在在线业务服务等级目标（SLO）可接受的前提下提高集群 CPU 和内存实际利用率。

测试采用“同一资源池、分阶段前后对照”：先建立仅有在线业务的基线，再逐级加入 BE 任务。所有结论都比较同一批节点、同一在线负载和相同观测窗口，避免小规模集群被拆分后样本过少。

## 2. 范围与假设

- 资源池包含恰好 10 个可调度工作节点，节点通过标签 `koordinator.sh/test-pool=colocation-10` 标识。
- 测试命名空间为 `koord-colocation-test`；在线与 BE 工作负载必须同时使用节点亲和性和资源池污点容忍，防止工作负载外溢。
- 集群已经安装可用的 `koord-manager`、`koord-scheduler` 和每节点一个 `koordlet`。
- 节点规格允许不同；测试强度以每个节点可分配资源的百分比表达，不依赖固定核数和内存容量。
- 本轮不使用真实业务。在线业务由 HTTP 服务模拟，离线任务由 CPU、内存和混合压力任务模拟。
- 测试不修改 Koordinator 核心代码，只新增可审计的测试清单、执行脚本、采集脚本和操作文档。
- 首轮只验证 CPU 和内存混部；磁盘、网络、GPU 和 NUMA 干扰不进入验收结论。

## 3. 方案选择

采用方案 1：10 个节点全部参与同池分阶段前后对照。

相比 5/5 并行对照，该方案保留完整资源池容量，减少调度离散性，并允许验证 BE 扩容、在线突增、压制和恢复的完整闭环。代价是测试时间更长，并且必须保持各阶段在线流量、镜像、配置和观测窗口一致。

## 4. 测试架构

### 4.1 资源池隔离

测试准备脚本接收 10 个显式节点名，逐一校验节点存在、Ready 且可调度，然后添加：

- 标签：`koordinator.sh/test-pool=colocation-10`
- 污点：`koordinator.sh/test-pool=colocation-10:NoSchedule`

测试工作负载具有对应容忍，并使用 required node affinity。脚本保存变更前的节点标签和污点，清理时只恢复本次测试改动，不覆盖节点已有配置。

### 4.2 模拟在线业务

在线负载由 Deployment、ClusterIP Service 和集群内压测 Job 组成：

- 每节点 2 个在线 Pod，共 20 个副本；使用 topology spread constraints 尽量均匀分布。
- Pod 使用普通 Kubernetes CPU/内存资源，不申请 BatchCPU/BatchMemory。
- HTTP 请求执行固定 CPU 计算并访问一块固定大小的常驻内存，使延迟同时对 CPU 争用和内存压力敏感。
- 初始稳定负载将池内 CPU 实际利用率维持在约 30%，内存实际利用率维持在约 35%。
- 压测器使用恒定到达率，避免服务变慢时请求自动减少而掩盖干扰；输出请求数、吞吐、错误率以及 P50/P95/P99 延迟。

在线基线应根据实测自动校准，而不是假定固定 QPS。校准以 5 分钟为一步调整并满足：P99 稳定、错误率低于 0.1%、CPU 利用率进入 25% 至 35%。

### 4.3 BE 离线业务

BE 工作负载使用 `schedulerName: koord-scheduler`、`priorityClassName: koord-batch` 和标签 `koordinator.sh/qosClass: BE`，申请扩展资源：

- `kubernetes.io/batch-cpu`
- `kubernetes.io/batch-memory`

负载分为三类：CPU 密集型、内存常驻型、CPU/内存混合型。每类使用独立 Deployment，便于逐级扩缩容。所有 BE 容器必须可被终止和重建，不保存业务状态。

BatchCPU 的数值按 Koordinator 当前接口使用整数 CPU 份额；BatchMemory 使用字节数量。实施脚本从节点 `status.allocatable` 读取池内实际 BatchCPU/BatchMemory，计算每个压力阶段可申请的总量，避免写死节点规格。

### 4.4 Koordinator 策略

仅对资源池节点启用混部策略，初始策略采用保守门槛：

- `enable: true`
- `cpuReclaimThresholdPercent: 70`
- `memoryReclaimThresholdPercent: 70`
- `memoryCalculatePolicy: usage`
- `resourceDiffThreshold: 0.05`

若现有 `slo-controller-config` 已包含其他节点级策略，实施必须使用 node selector 增加资源池专属配置，而不是替换整个 ConfigMap。执行前导出原配置，测试结束后恢复。

70% 是首轮安全起点，不是最终生产参数。只有在线 SLO 连续满足时，第二轮才能将回收阈值提升至 80%；95% 仅用于极限测试，不进入生产建议。

## 5. 分阶段测试流程

所有稳定阶段持续 30 分钟，前 5 分钟作为预热不计入统计；突增和恢复阶段按事件前后窗口统计。若任一安全停止条件触发，立即停止新增 BE 压力并缩容 BE 工作负载。

| 阶段 | 在线负载 | BE 目标强度 | 目的 |
|---|---:|---:|---|
| P0 环境检查 | 0 | 0 | 校验 10 节点、Koordinator 组件、指标和 Batch 资源 |
| P1 空载观测 | 0 | 0 | 记录系统与守护进程资源开销，持续 15 分钟 |
| P2 在线基线 | 100% 基准 QPS | 0 | 得到无混部的利用率、吞吐、错误率和延迟基线 |
| P3 低压混部 | 100% | 可回收资源的 30% | 验证 BE 可调度和基础隔离 |
| P4 中压混部 | 100% | 可回收资源的 50% | 验证目标收益区间 |
| P5 高压混部 | 100% | 可回收资源的 70% | 验证压制机制和 SLO 边界 |
| P6 在线突增 | 150%，持续 10 分钟 | 保持 P5 | 验证资源快速归还与在线优先级 |
| P7 内存压力 | 100% | 内存逐级升至可回收量 85% | 验证内存保护及 BE 驱逐，不制造节点 OOM |
| P8 单节点故障 | 100% | P4 强度 | cordon 并 drain 1 个测试节点，验证剩余节点承载和恢复 |
| P9 恢复 | 100% | 降至 0 | 验证在线指标在 5 分钟内回归基线区间 |

P8 只驱逐测试命名空间工作负载，并遵守 PodDisruptionBudget；不删除节点、不停止 kubelet，也不影响资源池外工作负载。若资源池节点上存在未授权业务 Pod，则跳过 P8 并在报告中标记。

## 6. 指标与计算方法

### 6.1 主要收益指标

- 池 CPU 利用率：`sum(rate(container_cpu_usage_seconds_total{node=~pool}[5m])) / sum(kube_node_status_allocatable{resource="cpu",node=~pool})`。
- 池内存利用率：节点工作集内存之和除以池可分配内存之和；排除 page cache 口径变化造成的虚假收益。
- BE 有效吞吐：BE 在观测窗口内完成的工作单元数或累计 CPU 工作时间。
- 回收资源利用率：BE 实际 CPU/内存用量除以 Koordinator 公告的 BatchCPU/BatchMemory。

报告同时给出池级加权利用率和 10 个节点的 P50/P95/最大值，不能只用节点百分比的简单平均掩盖热点。

### 6.2 在线业务保护指标

- 请求吞吐、成功请求数、HTTP 非 2xx 比例。
- P50/P95/P99 延迟，以及各阶段相对 P2 基线的变化率。
- 在线 Pod CPU throttling、OOM、重启和不可用副本数。
- 突增开始后首次恢复到基线区间的耗时。

### 6.3 Koordinator 行为指标

- 各节点 BatchCPU/BatchMemory allocatable 及其更新时间。
- BE Pod Pending、Running、Evicted、Failed 和重启数量。
- CPU suppress 前后 BE 获得的 CPU；内存压力下 BE 驱逐发生时间。
- `NodeMetric` 新鲜度、koordlet 抓取成功率和组件错误日志。

## 7. 验收标准

正式结论以 P2 与 P4 的 25 分钟稳定统计窗口为主；P5 至 P8 用于安全边界验证，不用于夸大稳定收益。

同时满足以下条件才判定通过：

1. P4 池 CPU 平均利用率相对 P2 提升至少 20 个百分点。
2. P4 池内存平均利用率相对 P2 提升至少 15 个百分点。
3. P4 在线 P99 相对 P2 增幅不超过 10%，且绝对 P99 不超过基线校准后确定的 SLO。
4. P4 在线错误率低于 0.1%，吞吐下降不超过 2%。
5. P3 至 P7 在线 Pod 不发生 OOM，非预期重启数为 0，可用副本不低于 95%。
6. P6 在线突增后，BE CPU 明显下降，在线 P99 在 5 分钟内恢复到基线的 110% 以内。
7. P7 允许 BE 被驱逐，但节点不得发生 MemoryPressure 持续 5 分钟、系统 OOM 或 NotReady。
8. P9 停止 BE 后，在线 P99、错误率和吞吐在 5 分钟内回到 P2 允许区间。

任何一个节点持续 3 分钟 CPU 超过 95%、内存超过 90%、出现系统 OOM/NotReady，或在线错误率连续 2 分钟超过 1%，均触发安全停止。

## 8. 数据完整性与判定规则

- 每阶段记录统一的开始时间、结束时间、配置摘要、镜像 digest 和 Pod 副本数。
- Prometheus 数据缺失超过阶段有效窗口的 5%，该阶段无效并重跑。
- 节点规格、内核、cgroup 模式或 Koordinator 版本不同的节点必须在报告中单列；不能将明显异构节点直接合并为单一结论。
- 每个稳定阶段至少重复 3 次，报告中给出中位数和最差一次结果。
- P2 基线在整个测试的开始和结束各执行一次；两次 P99 或 CPU 利用率差异超过 10% 时，说明环境漂移，本轮结果无效。

## 9. 安全、失败与回滚

- 默认先执行 dry-run，仅展示将修改的节点、ConfigMap 和工作负载。
- 节点标签、污点和 SLO 配置均在变更前备份；清理只逆转本测试创建的对象和字段。
- 每一阶段设置最长运行时间；压测 Job 或采集器异常退出时停止阶段，不自动继续加压。
- 安全停止按“停止压测器 → BE 缩容到 0 → 等待在线恢复 → 保存现场 → 判断是否恢复配置”的顺序执行。
- 测试命名空间、节点选择器和资源池节点清单是删除操作的三重边界；脚本不得对空节点列表或通配节点列表执行清理。

## 10. 实施产物

后续实施计划将产生以下可独立检查的产物：

- `hack/colocation-test/`：前置检查、资源池准备、阶段编排、数据采集、验收计算和安全清理脚本。
- `test/colocation/manifests/`：命名空间、在线服务、压测器、BE CPU/内存/混合负载及监控规则。
- `test/colocation/config/`：资源池节点清单示例、阶段参数和保守的 SLO 配置样例。
- `docs/manual-test/colocation-utilization.md`：从 dry-run 到回滚的操作手册。
- `test/colocation/expected/`：机器可读验收规则和报告结构样例。

实施不会自动在真实集群执行测试。操作者必须显式提供 kubeconfig、10 个节点名和确认参数，脚本才能执行会改变集群状态的步骤。

## 11. 非目标

- 不为生产业务直接给出最终回收阈值。
- 不验证真实业务特有的缓存、数据库、磁盘或网络尾延迟。
- 不自动安装 Prometheus、Koordinator 或集群依赖。
- 不跨资源池调度，也不修改资源池外节点。
- 不将一次测试结果直接外推到不同硬件、不同负载或更大规模集群。
